# 세부 분류 이름 충돌·삭제·합치기

2026-10-29. 사용자 화면의 ‘반팔 → 티셔츠’ 저장 실패는 이미 같은 상의 아래 기본 ‘티셔츠’가 있어 중복 이름 검사에 막힌 경우였다. 오류가 편집란에서 멀리 떨어진 하단에 표시되어 원인을 확인하기 어려웠다.

- 중복 이름과 서버 오류를 편집 필드 바로 아래에 표시하고 입력을 유지한다. 다른 이름으로 바꾸는 저장은 기존 CAS를 유지한다.
- 사용자 세부 분류를 기존 형제 이름으로 바꾸려 할 때 **기존 분류로 합치기**를 제공한다. 확인 뒤에만 원래 분류를 삭제하고 연결 의류를 대상 형제로 옮긴다. 대상의 기존 이름/사용 여부는 바꾸지 않는다.
- 사용자 생성 세부 분류 행에 휴지통 아이콘을 추가했다. 일반 삭제는 확인 후 의류를 같은 상위 종류로 옮긴다. 휴지통 의류도 포함하고 옷/사진/코디/착용 스냅샷은 삭제하지 않는다. 전역 기본 분류·종류의 삭제는 제공하지 않는다.
- `20261029134820_category_deletion.sql`은 20번째 migration이다. 소유자·leaf·대상/같은 부모·버전 확인, 회원 잠금과 NOWAIT 행 잠금으로 검사/이동/삭제를 한 트랜잭션으로 처리한다. `category_deletions`는 삭제 결과를 보관해 응답 유실 재시도를 동일 결과로 처리하고 과거 생성/수정 재시도의 부활을 차단한다. 직접 테이블 쓰기와 익명 실행은 허용하지 않는다.
- 타입은 실행 중인 로컬 PostgreSQL의 pg-meta에서 생성했다. Windows 앱 제어 정책이 기존 Supabase CLI 실행을 차단하여 로컬 migration/검증에는 기존 Docker DB를, 원격 적용에는 연결된 Supabase 도구를 사용했다. 정책을 변경하거나 CLI 차단을 해제하지 않았다.

검증: TypeScript/ESLint 및 단위 24개 파일 122개 통과. 실제 로컬 DB의 카테고리 통합 15개 통과(기존 9개 + 신규 6개). 중복 이름 재현/정상 수정, 삭제/동일 결과 재시도/부활 방지, 의류 2개와 코디·착용 기록을 유지하는 합치기, 상위 분류 이동과 다른 대분류 거부, 두 계정·익명·기본 분류·직접 쓰기 거부, 동시 수정/삭제 및 응답 유실을 검증했다. 테스트 과정에서 새 SQL의 UUID 형식과 nullable 부모 비교를 보완한 뒤 모두 통과했다.

운영 DB에 migration을 적용하고 함수 존재·회원 실행 가능/익명 실행 거부·삭제 테이블 RLS를 확인했다. 기존 의류 5개/사용자 분류 10개를 유지하며 실제 사용자 분류는 자동으로 변경·삭제하지 않았다. 로컬 fixture 계정/의류/사용자 분류/삭제 이력은 모두 0건으로 정리했다. 브라우저·실기기 직접 조작 검증은 기존 사용자 보류 범위를 유지한다.

운영 REST API에서도 새 RPC/테이블이 노출되고 익명 호출이 42501로 거부됨을 확인했다. 보안 advisor의 [인증된 SECURITY DEFINER 실행 안내](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable)는 기존 쓰기 RPC와 같은 의도된 경계이며, 함수 안의 인증/소유자/대상/버전 검사와 직접 테이블 쓰기 금지로 제한한다. 삭제 이력의 RLS는 활성 상태다.
