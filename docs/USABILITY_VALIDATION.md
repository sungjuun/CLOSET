# 실사용 점검과 저장 충돌 수정

점검: 2026-10-30, 마무리 확인: 2026-11-02. Q01의 웹 실사용 범위를 점검했다. 실제 집·회사 PC와 휴대폰을 모두 사용한 검증이나 네이티브 실기기 검증으로 간주하지 않는다.

## 확인한 범위

같은 배포용 웹 번들을 8082/8083의 서로 다른 origin에서 실행했다. 로그인 저장소와 Query 캐시가 독립인 두 세션을 같은 공용 Supabase에 연결해 기기간 사용을 모사했다. 별도의 임시 두 계정과 합성 사진 8장만 사용했으며 실사용자 자료를 수정하지 않았다.

- 한 세션에서 저장한 착용 기록을 다른 세션에서 새로고침해 조회했다. 날짜/메모 수정 뒤 새 날짜의 달력으로 복귀하고 기록 수가 갱신됐다. 이는 재조회 기반 동기화이며 실시간 구독을 추가하지 않았다.
- 두 세션이 같은 버전을 편집할 때 최신 저장을 덮어쓰지 않고 충돌을 안내하며 작성 중인 메모를 보존했다. 명시적인 최신 내용 교체로만 초안을 바꾼다.
- 기록할 코디 미선택 오류, 저장 전 메뉴 이탈 확인, 계속 편집/키보드 Tab 이동, 이름 있는 확인창을 확인했다.
- 프로필 이름과 다크 테마를 저장한 후 다른 세션에서 다시 읽어 복원했다. 다른 테스트 계정으로 전환하면 옷장과 통계가 0으로 바뀌며 이전 계정의 기록 주소 접근도 차단된다.
- 1280px PC, 390/320px 모바일 웹에서 확인했다. 통계/설정/달력의 가로 넘침, 윤년 2월 29일과 월 이동, 잘못된 2월 30일 입력의 오류/입력 보존을 확인했다.
- 320px에서 10월의 ‘다음 달’ 버튼이 다음 줄로 밀리는 문제를 수정했다. 좁은 화면은 접근성 이름이 있는 44×48px 화살표 버튼을 사용한다. 이전/다음 버튼의 y 좌표가 같은 것을 확인했다.

## 통계 대조

2026-10-30을 기준일로 고정하고 8/1, 9/1, 10/1, 11/1 기록과 UI에서 생성해 10/29로 수정한 기록을 사용했다. 준비 당시 11/1은 미래이며 기준일 이후 기록 제외 여부를 확인했다.

| 항목 | 기대/확인 값 |
| --- | --- |
| 30일 / 90일 / 전체 기록 | 2 / 3 / 4개 |
| 현재 의류 / 구매가 입력 | 8벌 / 2벌 |
| 구매가 합계 | 180,000원 |
| 상의 누적 착용당 비용 | 120,000원 ÷ 4회 = 30,000원 |
| 하의 누적 착용당 비용 | 60,000원 ÷ 3회 = 20,000원 |

생성한 테스트 기록을 API에서 삭제한 후 30일 기록 1개, 상의 3회/40,000원, 하의 2회/30,000원으로 다시 집계되는 것도 대조했다. 코디·의류·사진은 유지한다.

## 발견한 저장 지연과 수정

공용 API에서 업무상 버전 충돌을 SQLSTATE `40001`로 반환하면 요청이 오래 대기하고 결국 일반 네트워크 안내로 표시되는 문제를 재현했다. Supabase의 [공식 안내](https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions)에서 PostgREST가 해당 코드를 재시도 대상으로 처리하는 것을 확인했다.

`20261030052619_nonretrying_business_conflicts.sql`로 17개 기존 함수의 업무상 충돌 코드 24곳을 `PT409`로 변경했다. [PostgREST의 HTTP 오류 코드 방식](https://docs.postgrest.org/en/stable/references/errors.html)에 따라 HTTP 409를 즉시 반환한다. 함수 서명·인증·소유권·버전 비교·잠금·재시도 결과 확인·실행 권한은 유지했다. 기존 migration은 변경하지 않았고 새 migration 한 개를 로컬과 공용에 적용했다. 실제 트랜잭션 직렬화 오류 자체를 변환하는 것은 아니다.

앱의 의류 외 코디·착용·브랜드·카테고리·설정 충돌 안내는 새 `PT409`와 기존 `40001`을 함께 인식한다. 공용 API의 오래된 버전 요청은 66ms에 HTTP 409/PT409를 반환했고, 새 번들에서도 충돌 안내와 입력 보존을 다시 확인했다. 공용 DB의 앱 함수에 수동 `40001` 코드가 남지 않은 것도 조회했다. 점검 종료 시 해당 RPC로 대기 중인 backend가 없어 연결 강제 종료나 프로젝트 재시작은 하지 않았다.

착용 폼의 메뉴 이동 안내를 목적지와 무관한 문구로 고치고 확인창에 접근성 이름을 추가했다.

## 자동 검증 및 남은 확인

- 타입 검사, ESLint, 단위 테스트 192개 통과.
- 로컬 DB 회귀 149개(Node 13 + Vitest 136) 통과. 추가 테스트는 오래된 버전이 3초 제한 안에 HTTP 409/PT409를 반환하고 원본 메모를 보존하는 것을 확인한다. 다른 충돌 경계의 기존 기대 코드도 새 계약으로 갱신했다.
- Android/iOS JS export, 공용 웹 빌드와 공개 산출물 검사를 통과했다. 로컬 보안 advisor 경고 없음. 새 테이블·권한·환경 변수·외부 서비스는 추가하지 않았다.
- 캡처는 제외된 `test-results/usability-conflict.png`, `usability-insights-desktop.png`, `usability-insights-mobile.png`, `usability-calendar-mobile.png`에 보관한다.
- 테스트 계정/데이터/파일은 정확한 fixture 소유자와 경로만 대상으로 정리한다.

실제 휴대폰 Safari/Chrome, 네이티브 카메라·사진 선택·공유 시트·백그라운드 복귀, VoiceOver/TalkBack, 실제 두 장소의 네트워크 전환과 느린/오프라인 환경은 후속으로 남는다. 따라서 Q01 전체를 완료로 표시하지 않는다. 실제 기기 확인 전에는 백업/복원과 운영 파일 정리 등 별도 후속 작업도 남아 있다.
